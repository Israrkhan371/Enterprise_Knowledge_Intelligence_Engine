Choosing a Vector Database

Ezitech Engineering Blog

When we scoped EKIE's embedding pipeline, the vector database choice came down to three realistic options: ChromaDB, Pinecone, and Weaviate. Here's what actually drove the decision, not just a feature checklist.

ChromaDB

Runs embedded or as a lightweight local service, which matters a lot for a project that needs to run entirely via docker-compose without external accounts or API keys. Metadata filtering (category, source type) is straightforward, and it's simple enough that onboarding a new engineer to the vector store takes minutes, not a half-day reading someone else's cloud console.

Pinecone

A managed, cloud-hosted vector database with strong scaling characteristics for large production workloads. The tradeoff for a project like this is that it requires an external account, has usage limits on the free tier, and introduces a network dependency for every single search — not ideal when the goal is a self-contained, reproducible development environment.

Weaviate

Feature-rich, with built-in hybrid search and a GraphQL API, but heavier to operate — it wants its own dedicated service with more configuration surface than a project this size needs, and much of its hybrid-search functionality overlaps with what EKIE already implements directly via reciprocal rank fusion over semantic and keyword results.

The decision

ChromaDB won for EKIE: local-first, no external account required, good-enough metadata filtering, and low operational overhead for a docker-compose-based dev environment. Pinecone or Weaviate would be reasonable choices for a production deployment at much larger scale, which is explicitly out of scope for this case study.
